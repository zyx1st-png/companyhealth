# CASE-002｜客户建档与需求管理30天执行计划 V1.0

**执行范围**：日常服务反馈、基础客户建档、需求分类、人工交接、WorkBuddy内部辅助及周期复盘。  
**状态**：待经营方批准的计划，不代表已实施。  
**不纳入**：整店盈利和场地诊断、集中营销邀约、付费健康管理计划、疾病诊断、病史采集、医保或养老补贴业务开发、自动给外部联系人发消息。

## 0. 开工前责任与门槛

| 任务 | 责任角色 | 验收标准 |
|---|---|---|
| 数据字段与合法用途 | 经营方数据负责人 | 列明来源系统、可用字段、处理目的、访问权限，未经确认不迁移真实个人数据 |
| 现场执行条件 | 侯姐 | 护士固定工作设备、独立账号、网络和培训时段 |
| 需求接收及升级 | 侯姐 | 指定负责人、替补和餐饮/理疗接口人 |
| 系统流程 | 顾问远程 | 权限校验、拒绝联系、日志、备份和故障退化可演示 |
| AI处理边界 | 系统管理员与经营方 | 只处理获得适当授权且必要的业务信息，模型供应商与处理环境已检查 |

任一关键门槛不满足时只进行模拟开发或适当条件下的匿名意见统计，不安排真实客户数据导入与正式服务工单。

## 第1周（D1—D7）｜信息盘点与SOP

- **D1 业务确认**：明确实际试点接触点为现有食堂与合法理疗服务；不以健康会员计划邀约客户。
- **D2 历史数据盘点**：仅盘点表头、记录总量、日期范围、缺项和去重规则；在原有合法控制环境下计算汇总，不向AI提交真实个人明细。
- **D3 数据字典**：设计客户基础档案、联系许可、反馈、需求、任务及审计记录。
- **D4 岗位与授权**：明确护士、数据管理员、餐饮接口人、理疗接口人、投诉处理人及替补和远程顾问的权限。
- **D5 标准话术**：形成食堂2—3题匿名反馈、理疗服务体验反馈、客户自愿留资告知、复杂问题转交卡。
- **D6 设备和安全**：检查设备、独立登录、网络、文件存储、权限、退出、备份及纸质应急流程。
- **D7 阶段核验**：确定P0模拟开发的正式需求边界。

**交付**：《字段目录》《数据字典》《权限矩阵》《护士操作卡》《问题升级规则》。

## 第2周（D8—D14）｜WorkBuddy原型与模拟

| 时间 | 工作 | 可核验结果 |
|---|---|---|
| D8—D9 | 建立Customer、Permission、Feedback、Need、Task、AuditLog六类结构；允许匿名反馈无客户ID | 表单可演示，必填与权限校验通过 |
| D10—D11 | 护士四入口：今日反馈、自愿建档、待交接、异常升级；一步一问 | 新手按固定话术和选择项录入 |
| D12 | 确定性规则：拒绝/撤回阻断、无负责人不能结单、诊疗字段禁止录入、重复和越权保护 | 规则自动测试可复现 |
| D13 | WorkBuddy分类建议、漏项检查、到期提示、日报周报草稿 | AI停机后基础表单仍能运行；数字由程序计算 |
| D14 | 10个完全虚构端到端案例 | 通过并形成测试记录、问题和修复清单 |

**十个案例**：匿名满意、匿名投诉、自愿留资、拒绝留资、重复客户、理疗预约意愿、超出范围需求、无人接单、撤回许可、系统/AI失效。

**P0门槛**：关键安全及状态测试全部通过；护士可独立完成至少8个正常模拟案例；异常能够正确升级。不因软件完成而自动批准导入历史会员。

## 第3周（D15—D23）｜自然服务场景试点

**启动条件**：经营方确认合法处理依据、设备与负责人就位，系统权限和日志演示通过。

**食堂**：自然营业场景下自愿完成匿名2—3题反馈，允许拒绝。仅客户愿意且完成必要告知、合法处理依据充分时才建基础档案。统计“反馈份数”和“独立已建档人数”分开。

**理疗**：在合法正常服务接触中问服务体验、预约意愿和改进建议，不将患者病情、诊断、处方或医保内容录入本系统。

**每天执行**：服务接触→记录匿名反馈或自愿建档→需求分类→提交→主管/服务人员接收→反馈处理→护士确认完成。超出范围的事项只能转主管评估，不能承诺必能提供新服务。

**样本目标**：20—30份符合处理条件的真实反馈或基础档案记录；不足则报告真实数量及原因。不能把同一人重复记录、每日食堂人次和新建档人数混算。

**监督**：护士每日核对未提交事项，承接人每日核对待处理需求，顾问每周只看经批准的汇总与流程障碍。

**暂停条件**：越权访问、不当处理健康信息、擅自营销、服务无人接收导致严重积压或出现重大投诉。

## 第4周（D24—D30）｜分析与持续运营基线

- **D24—D26** 汇总客户数据字段完整度、匿名反馈量、自愿建档量、需求分类、任务承接率、逾期、投诉、护士工作耗时与返工。
- **D27—D28** WorkBuddy整理相似需求，逐条保留来源及证据强度；经营方和顾问人工校准。无真实订单数据，不计算所谓增量收入。
- **D29** 召开一次远程复盘，核对护士操作难度、客户拒绝原因、需求承接问题及字段冗余。
- **D30** 输出《客户与服务反馈基线 V1.0》《需求观察简报》《护士SOP V1.0》《下一阶段继续/调整/暂停建议》。

## 核心数据表（最小字段）

| 数据对象 | 最小字段 |
|---|---|
| Customer | 客户ID、称呼、必要联系方式、来源、档案状态（仅适当处理依据下） |
| Permission | 联系用途、依据及时间、拒绝/撤回状态、证据引用 |
| Feedback | 反馈ID、场景、日期、服务评价、匿名标记、非敏感备注 |
| Need | 类别、反馈来源、需求摘要、当前状态、负责岗位 |
| Task | 任务ID、责任人、截止时间、接单状态、处理结果 |
| AuditLog | 操作人、时间、对象、动作、必要状态变更 |

**状态流转**：反馈→待分类→待派发→待接收→处理中→已处理/已取消/已升级。匿名意见可进入聚合分析而不形成可识别个人工单。

## WorkBuddy需求

- P0：表单与字段检查、护士操作向导、分类建议、确定性到期提醒、内部日报周报、权限和日志。
- P1：重复客户提示、负责人超时提醒、复盘问题聚类及SOP修订建议。
- 条件性后期：历史会员最小非医疗字段合法受控导入。
- 禁止首期：自动营销外呼、智能疾病诊疗、自动分析医疗资料、未经批准的跨系统数据同步。

## 验收与待决策

**是否值得继续**，重点看护士独立操作、信息准确、需求有人承接、客户自愿反馈、任务闭环、实际人工耗时和可重复性，而不是只看建档条数。

侯姐仍需确认：数据合法用途负责人、护士具体设备、需求处理专人及替补、餐饮/理疗接口、服务承诺范围、WorkBuddy账号和数据部署、远程顾问工作量/费用/退出安排。
