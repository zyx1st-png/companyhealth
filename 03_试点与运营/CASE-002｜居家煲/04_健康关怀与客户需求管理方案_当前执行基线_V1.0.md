# CASE-002｜居家煲健康关怀与客户需求管理方案 V1.0

**版本**：V1.0｜当前执行基线（方案已整理，待经营方确认启动条件）  
**日期**：2026-10-18  
**服务对象**：贵州居家煲生活服务有限责任公司  
**项目性质**：企业伴随式服务专项——客户基础建档、日常服务关怀与需求感知、WorkBuddy 辅助执行  
**证据状态**：已知条件主要来自项目方提供的企业资料截图与口述，尚未取得经营方逐项确认和真实实施证据；不把计划写为实绩。  
**本文件层级**：本专项的**当前统一业务/操作/开发口径**。背景事实细节见01；首诊证据和限制见02；逐日安排见03。原 D07 已废止，不再强制企业级资料匿名分仓。仓库虽可保存完整企业级资料，但仍为公开仓库，必须保护不宜公开的个人资料及第三方权益。

## 1. 一句话方案与现阶段目标

围绕现有餐饮和理疗服务接触，建立**资料来源明确、反馈记录标准化、需求有人承接、执行情况可追踪**的基础客户运营能力；由坐班护士执行简单步骤，WorkBuddy 只做内部辅助、提醒和汇总，远程顾问定期复盘。

**第一阶段目标**：看清现有客户数据结构、积累真实服务需求、建立岗位闭环、验证可持续执行。  
**不是第一阶段目标**：以健康管理名义销售新产品、集中邀约老客户、把原医疗档案全部转成营销客户、开展专业诊疗、保证新增营收或代管整个门店。

### 已知启动条件与限制（以经营方核验为准）

| 事项 | 当前项目方所知 | 实施影响 |
| --- | --- | --- |
| 历史会员 | 约600名，资料所在系统可导出部分基础字段 | 先做原系统内的字段盘点、去重和用途核验；人数非已核实独立客户数 |
| 社区食堂 | 午餐12元左右，每天100多人次；目前只有订单/人次汇总 | 先匿名征求服务意见；不能计算个人复购或直接建一人一档 |
| 理疗服务 | 已有历史服务关系与现场服务人员 | 先收体验/预约需求，不处理诊断、处方、医保或治疗疗效判断 |
| 坐班护士 | 人员已确定，但工作设备和账号不齐全 | 需要简单工作台、标准话术和操作训练 |
| 需求升级 | 负责人及替补尚未明确 | 未明确前不能宣称需求处理闭环可上线 |
| 对外活动 | 暂时不组织专门邀约，不推广健康关怀会员计划 | 只利用自然到店及合规的正常服务沟通 |

## 2. 服务范围和客户体验

### 2.1 首期提供的真实服务

1. **基础客户资料规范**：在符合信息处理条件时核对必要称呼、服务来源、联系意愿、客户编号及资料质量。
2. **日常服务反馈**：请客户评价现有餐饮或理疗服务及提出改进建议。允许不留姓名。
3. **需求采集**：记录当前需要什么、哪里不方便、希望门店改善什么；“暂无需求”也是有效反馈。
4. **服务衔接**：现有餐饮/合法理疗范围内的预约或意见由责任人接收；超出范围的内容登记为“待评估”，不承诺提供。
5. **后续关怀**：只按客户意愿、合法联系依据和具体服务需要安排，允许拒绝、暂停及撤回。

### 2.2 首期不提供

疾病筛查、专业健康档案、风险评分、用药方案、医疗诊断治疗、医保结算指导、养老补贴核销、未经验证的新服务包、外部客户自动营销，以及以“免费医疗检查”引流的活动。

当前名称建议：**对内称“客户健康关怀与需求管理”**；员工对客户只说明“日常服务体验反馈、服务需求登记”。未来正式推广“老客户健康关怀与服务回访计划”，需在真实服务与告知材料准备后另行确认。

## 3. 客户资料三条入口和一套记录原则

| 入口 | 原始来源 | 首期允许的工作 | 形成的数据 |
| --- | --- | --- | --- |
| A 历史会员数据盘点 | 原业务/医疗系统 | 在有权限的原环境盘点字段、记录总量、时间跨度、重复与缺失；逐项核实再利用目的和依据 | **匿名汇总/字段目录**，不直接导入医疗原始记录 |
| B 食堂自然服务 | 正常用餐过程 | 自愿的匿名简短体验调查；愿意留资时先完成必要告知与合法处理条件核验 | 匿名 Feedback；或单独创建自愿基础档案 |
| C 理疗自然服务 | 正常服务结束后 | 回顾服务体验、预约便利性、改进建议，转交明确服务需求 | 不含诊断及病史的 Feedback / Need / Task |

**最重要的口径**：食堂“100多人次”不等于不同顾客数；“约600条记录”不等于600名经授权可营销客户；可导出不等于可以向WorkBuddy提供患者资料。

客户可以只提供匿名反馈。**匿名反馈份数、自愿建档人数、需求记录条数**分别统计，不能混加为新增会员。

## 4. 一次客户接触的服务与操作SOP

**标准流程**：合规接触 → 说明来意 → 客户选择匿名反馈或自愿建档 → 护士按选项登记 → 系统校验 → 如有需求生成内部任务 → 指定负责人接收 → 处理反馈 → 完成或升级。

### 4.1 护士四个工作入口

1. **今日服务反馈**：按照场景打开简短表单。
2. **自愿客户建档**：核对必要资料、联系偏好与处理依据，不录入病史、诊断和医保信息。
3. **待交接需求**：查看是否已分类、交付给谁、何时到期，提醒相关人员确认接单。
4. **异常/投诉升级**：遇到不知道如何处理、客户不满、无法承接或越过服务范围的事项，点击“转主管”。

**单条操作**：打开任务 → 查看话术和上下文 → 向客户说明 → 选择结果 → 审核内容 → 保存 → 查看下一步。护士不能为了完成指标编造反馈。客户拒绝即按规则结束。

### 4.2 现场建议问题（灵活询问，不机械盘问）

- “您觉得我们这次服务怎么样？有没有不方便的地方？”
- “现在餐饮或理疗服务方面，还有什么需要帮助或改进的？”
- “这次意见需要我们帮您进一步转交处理吗？”

仅当客户主动愿意留下联系信息且完成相应告知后，才询问必要的联系方式及未来联系意愿。不主动询问病史、用药、医保待遇或病症。

### 4.3 负责人交接

- **护士**：忠实记录、固定分类、提交与追踪，不擅自承诺价格或新服务。
- **餐饮/理疗接口人员**：接单、确认能否提供既有服务、记录办理结果。
- **复杂需求/投诉专人及替补**：由侯姐指定；处理超范围问题、争议及无人承接事项。
- **侯姐**：负责指派、权限批准、服务范围确认和例外经营决定。
- **远程顾问**：WorkBuddy流程搭建、脱敏周报与SOP改进；不代替现场人员处理客户，不承担临床责任。

未指定负责人时，系统只能把任务留在**待指定/待处理**，不能自动标记为已解决。急性危险情况应按紧急服务预案及时转介急救，不等待AI审批。

## 5. 核心数据结构与操作权限

| 数据对象 | 最小字段 |
| --- | --- |
| Customer | 内部客户ID、必要称呼和联系渠道（仅合法可用时）、来源、档案状态、更新时间 |
| Consent / Permission | 处理目的、依据与时间、联系偏好、拒绝或撤回状态、证据位置 |
| Feedback | 反馈ID、场景、日期、匿名标识、非敏感评价、改进建议 |
| Need | 需求ID、服务类别、来源反馈、简要内容、状态、是否超出范围 |
| Task | 负责人/岗位、期限、接单与完成状态、处理结果、升级记录 |
| AuditLog | 操作者、动作、时间、必要前后状态 |

**基本规则**：拒绝/撤回优先阻断；限制重复任务；无授权不自动触达；无责任人不能完成交接；禁止AI擅自更改客户事实；关键操作保留审计日志。

**权限**：护士只访问获分配的合法业务资料；服务人员只访问其任务必要信息；主管审核跨岗位事项；远程顾问默认接触脱敏或汇总数据，不持有医疗系统原始资料。

## 6. WorkBuddy开发功能清单（分期）

| 优先级 | 模块 | 功能与验收 |
| --- | --- | --- |
| P0 | 表单与数据 | 匿名反馈、基础自愿建档、需求登记、字段校验、去重提示、状态与权限 |
| P0 | 护士工作台 | 四类入口、固定话术、选择式操作、一键升级、未提交提醒 |
| P0 | 需求任务 | 分类、指定责任人、接收/拒绝、超时/撤销、办理反馈、不可处理状态 |
| P0 | 安全与追溯 | 权限、勿扰/撤回、操作日志、备份、AI不可用的手工退化流程 |
| P0 | 基础分析 | 匿名反馈量、自愿建档量、需求类别、未承接事项、真实耗时（代码统计） |
| P1 | AI辅助 | 信息整理草稿、遗漏字段提示、内部周报、相似需求聚合建议 |
| P1 | 经营复盘 | 问题高频主题、岗位瓶颈、SOP修订建议及版本历史 |
| 后期按条件 | 受控历史字段导入 | 需另行核实原数据处理主体、合法使用目的、第三方处理及权限条件 |
| 不在首期 | 外部联系人自动消息、AI诊断、付费健康会员、医疗记录分析 | 不开发 |

实现方式先验证 WorkBuddy + 有访问控制的持久化表格/数据库。重要数据必须保存在可靠的数据层，不能只存于聊天上下文。对于权限、客户许可、任务状态和报表计数，必须由确定性规则与程序处理；AI只能辅助写摘要或建议。

## 7. 30天试点步骤

| 日期 | 主要事项 | 交付及门槛 |
| --- | --- | --- |
| D1—D7 | 资料源与字段盘点、合法用途确认、设备账号、负责人和接口人员安排；定稿SOP | 数据字典、权限矩阵、护士话术与升级规则 |
| D8—D14 | WorkBuddy原型、内部任务、审计及10个完全虚构的端到端案例 | 核心流程可执行；安全及拒绝规则测试通过 |
| D15—D23 | 前述启动门槛满足后在自然服务过程中收集20—30条真实、合规的反馈或基础档案 | 现场操作、真实来源和责任承接可追踪；不足如实记录 |
| D24—D30 | 汇总需求类型、匿名反馈、任务闭环、护士耗时、记录缺失与客户意愿；远程复盘 | 首轮需求观察报告、客户管理基线及SOP修订V1.0 |

**10个模拟测试必须覆盖**：匿名好评、匿名投诉、正常自愿建档、拒绝提供联系方式、重复客户、餐饮/理疗需求、超出服务范围、无承接人、撤回联系意愿、AI或网络故障。

## 8. 验收与价值判断

**执行达标**：护士经过培训能独立完成绝大多数模拟常规任务；拒绝、权限、撤回及异常流程正确；现场有责任人承接；报表能追溯来源。

**数据达标**：每条记录可区分“匿名反馈/已核实基础档案/实际服务任务”；反馈与建档分别统计；关键数据不靠AI自行补写。

**经营价值**：能够呈现客户反复提出的问题、未满足的服务需求、现有服务可改善环节，以及具体跟进结果。即使尚无新增成交，也应能说明项目的管理效用、员工投入和继续建设是否划算。

**可持续性**：顾问无需到场，护士和现场人员能继续操作，经营方能读懂周期报告。

本阶段**不以**“600会员全部迁移”“新增营业额必达”“必须建成专业健康管理业务”作为验收条件。

## 9. 尚待侯姐与项目方确认的事项

1. 历史资料的处理主体、许可范围、可导出字段、可用目的和必要告知。
2. 护士设备、个人账号、固定班次、资料存储位置、权限与备份。
3. 需求处理负责人、替补，以及餐饮/理疗具体承接岗位与处理时限。
4. 服务反馈真实问法、业务目录与必要服务责任；投诉/突发事项转介流程。
5. WorkBuddy使用环境、模型服务方、信息处理条件、隐私与安全措施。
6. 远程顾问合作费用、工时上限、阶段成果、验收方式与退出交接。

这些均是**待确认的执行或合规条件**，未因本文件发布被视为已批准。

## 10. 项目总结

**第一阶段交付的是长期有用的客户运营能力**：资料可管理、意见可记录、需求可分析、人员可执行、任务可跟进。未来的健康管理会员、养老服务、新业务或营销活动，只有在客户真实需求、履约能力、适当资质与经营方单独决策具备后，才进入新的项目阶段。
