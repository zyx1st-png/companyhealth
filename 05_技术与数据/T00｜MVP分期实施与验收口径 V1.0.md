# T00｜MVP分期实施与验收口径 V1.0

**文件性质：技术与业务之间的范围控制。** 现有MVP的9模块和6张表是候选范围，不表示代码已开发；T02是目标架构而非一次性交付需求。

## 1. 不以完整平台上线阻断市场验证

- **L0手工可控闭环（先实施）**：匿名/经授权企业档案、人工导入Excel/CSV、确定性指标计算、固定模板与AI文本初稿、逐企业人工审核、手工发送并记工时。优先验证2–3家真实客户可服务性。
- **L1最小内部工作台（在L0稳定后）**：company_id隔离、资料来源与版本、导入去重、任务队列、报告审批、修改原因/工时、可追踪已发送状态。以真实试点重复痛点选模块；无须立即全做9模块。
- **L2批量试验**：按T01 E01/E02/E03使用虚构20家企业进行批量与逐家AI辅助质量对齐测试；成功才考虑更广泛调度、外部政策匹配及高级驾驶舱。
- **L3可能的受控集成**：WorkBuddy/MCP、微信文件自动获取或企业微信平台接口须分别验证接口、授权、稳定性、合规、错误恢复与成本；未通过不纳入P0。
- **禁止从周报文字修改率低直接升级自动对外发送**；本阶段正式发送由顾问人工确认。

## 2. 首个真正能跑通的垂直切片

1. 使用虚构企业A与B建立独立 company_id、独立资料目录和授权状态。
2. 人工放入3份不同格式、含重复或缺失字段的样例数据；无法判定企业归属时进入待归类，不能猜测。
3. 只实现1个行业中的1–3项可重复指标（推荐商贸的收入/应收，或餐饮的渠道结算）；计算结果与手工参考值一致。
4. 生成一份含“事实/观察/推断/建议、来源与缺失说明”的草稿，关键数字由程序填入。
5. 人工复核公司身份、数字、权益、建议；生成批准/退回记录及人工分钟。
6. 人工复制并发送到**确认过的**客户渠道，事后手工标记已发送；严禁自动发错对象或模拟结果当真实成果。

**验收**：A/B客户资料不混用；缺失字段不计算成0；错误有日志且可复测；对外前可暂停；人工时间可统计；真实资料仅在合法授权后处理。未达到安全底线不能进入真实数据实验。

## 3. 对旧MVP几处过期口径的明确修订

| 旧MVP说法 | 本阶段有效解释 |
|---|---|
| “两周开发完” | 原规划**挑战目标**，不是客观承诺；以垂直切片验收决定排期 |
| “每周1–2小时服务5–10家” | 仅待验证的某些周期性任务目标；不含获客、首次体检、完整会员问诊与客户关系管理 |
| “退出后统一7日删除全部” | 错；按D04与G06草稿分类处置，经合同/法律确认保存、返还、删除与备份 |
| “低修改率以后自动发送” | 错；必须先有渠道许可、明确授权、任务风险分类、可靠收件人确认、错误回滚与独立质量验证 |
| “数据不出境/国内模型” | 初期选型意向；实际数据流、供应商条款、处理地点及是否可以传输客户摘要均须单独审查 |
| “企业统一健康总分” | 禁止总分；采用状态标记与证据缺口 |
| “周报P0必须完全自动接收微信文件” | 改作L1/L3条件功能；初期可先人工导入确保业务验证 |

## 4. 自动化任务的最小数据实体

至少记录：企业、授权状态、原始资料ID及哈希、指标及口径版本、任务与状态、交付版本、审核日志、人工分钟、实际发送确认、客户行动反馈。所有企业私有内容均按company_id限制查询、导出及AI上下文；共享信息只能是合法可共享的公开资源。

## 5. 技术工作应如何排序

先解决**错算、错客户、资料不明、人工审核无记录**，再解决**速度和重复操作**，最后才讨论**自动推送/完整驾驶舱/微信接口**。任何“AI多智能体、自动检索全库、自动发微信”的设想都不应绕过最小必要与数据授权原则。

T01的目标：20份模拟周报人工总时间≤180分钟且相对逐家AI辅助减少≥40%，同时严重资料混入/关键数字编造/权益错误为0。它证明的最多是**特定任务的批量效率**，而不是整家企业服务月工时、自然客户留存或系统已投入生产。

## 6. 与其他文件的关系

MVP需求列功能候选；本T00界定**实现顺序与安全门槛**；T02列远期架构；D04为服务的业务标准；F01/V00为商业验证。发生细节冲突时标为待决，不允许AI擅自扩大授权或取消人工审核。
