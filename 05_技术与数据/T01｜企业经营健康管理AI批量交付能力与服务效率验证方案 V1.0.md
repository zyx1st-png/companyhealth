# T01｜企业经营健康管理AI批量交付能力与服务效率验证方案 V1.0

**副标题：从单企业AI辅助，到多企业低边际成本服务**

**项目：** 企业经营健康管理\
**版本：** V1.0\
**阶段：** 技术交付能力验证\
**依据：** C02 V1.1、B02 V1.1、B03、B03-1、B04系列、D01、D04\
**性质：** 内部实验设计与MVP验收参考，不代表已完成实验；2026-10-13新增B06两档企业日常事务交付验证，不允许通过模拟推导商业付费能力

# 一、验证目标

## 1.1 核心假设

本项目的核心效率假设是：

**多个企业可以共享同一套信息处理、行业分析和任务执行能力，同时保留独立的企业上下文和经营数据。**

在这种情况下，新增一家企业所需要的额外工作，可能显著小于为该企业从头完成全部服务的工作量。

但不能仅凭AI可以批量生成文字，就认定已经具备规模化交付能力。

因为真实交付还包括：

- 数据准备与更新
- 客户身份及套餐识别
- 信息来源核实
- 经营数字计算
- 企业个性化解释
- 人工审核
- 客户沟通
- 服务记录和行动跟进

因此，实验必须把这些工作纳入评价。

## 1.2 本次验证的五个问题

**问题一：共享信息能否一次处理、多企业匹配？**

**问题二：20家企业的个性化周报能否集中生成并高效审核？**

**问题三：同一行业的多家企业能否共享分析程序，却使用各自独立的数据？**

**问题四：AI减少的人工时间，是否大于它新增的检查、修正和维护时间？**

**问题五：在满足现有服务标准的情况下，能否支持C02 V1.1提出的低边际成本模型？**

## 1.3 本次暂不验证什么

T01不直接证明：

- 企业一定愿意购买199元或399元会员
- 企业会长期续费
- 协会一定能够介绍付费客户
- 所有行业都具备相同自动化效率
- 创始人已经能够独立服务50家企业
- AI可以取代人工经营判断

以上问题需由后续真实商业试点或其他专项验证回答。

# 一-A、新增实验E05｜企业日常经营事务支持质量与人工容量（2026-10-13）

目标：验证企业自然语言交办能否以AI辅助稳定完成九类小型经营事务，不只生成营销文案与宣传图。采用**日常快办**与**定制处理**二档，1复杂按3轻量互替；新客户199每周1复杂或3轻、399每周2/6、1299起每周3/9；免费M-L0只有一次快办。所有模拟案例和真实客户须分别标识，不能互当证据。

建议至少覆盖：推广图文、客户/销售、办公会议、人事招聘、经营问题、市场政策、采购合作、数据表格、培训/流程。每类构造若干**虚构**且边界清楚的请求，提供明确的输入、应交成果、可靠事实来源和允许修改次数；客户原始资料仅经适当授权导入隔离的实际运营空间。

记录任务类别、人工审核前后差异、首响应与实际交付时间、平均/P90总人工分钟、客户是否真正采用交付物、修改次数、模型边际成本、错引/幻觉及隐私越界。内部验证目标为快办人工5–10分钟、定制15–30分钟；若超出，应提升任务等级、限量或专项报价，**不是跳过人工核验来满足时间**。每周额度用简单任务登记表即可，无需先开发积分兑换或自动微信发信系统。客户沟通、审核和返工均计入全链路工时。

此E05为**待执行的新实验**，原E01–E04不因新增而视为已经完成；真实付费与留存另依V00/V01。

# 二、实验的共同技术原则

## 2.1 建议采用五层能力

**第一层：企业经营档案**

每家企业独立保存行业、经营模式、主要问题、关键指标、服务权益、行动事项及数据授权。

**第二层：共享信息资源库**

统一管理经核实的政策、行业信息、商机和公共资源。

**第三层：确定性计算和规则引擎**

负责数值计算、数据去重、日期比较、条件核对和业务规则。

**第四层：AI生成与分析**

负责信息理解、个性化匹配、解释、报告草稿和需要人工核实的异常提示。

**第五层：人工审核工作台**

负责重要判断核实、服务范围确认、异常处理、正式发送和交付留痕。

核心结构：

**共享规则和公共信息，隔离企业数据和个性化上下文。**

## 2.2 不以完整SaaS开发为前提

首轮允许使用：

- WorkBuddy或现有AI工作流工具
- 结构化表格
- 独立企业文件空间
- Python或其他可靠计算程序
- 简单批量任务脚本
- 人工审核及发送

本次目标是证明流程的质量和效率，不是先证明能够开发大型软件系统。

## 2.3 与现有服务标准保持一致

B02与D04已经要求：

- 重要经营数字可追溯
- 正式重要分析由顾问审核
- 企业数据独立管理
- 不因资料不足制造确定性结论
- 服务内容符合实际套餐权益
- 重要事项进入持续跟进流程

T01不能通过跳过这些要求来缩短人工时间。

# 三、统一实验样本

## 3.1 建立20家模拟企业档案

建议首轮使用20家虚构测试企业。

| 行业      |      数量 | 主要测试内容        |
| ------- | ------: | ------------- |
| 商贸批发与经销 |      8家 | 应收、库存、客户、供应链  |
| 餐饮与门店   |      6家 | 营业额、渠道、平台费用   |
| 工程与项目服务 |      4家 | 合同、进度、回款、项目机会 |
| 专业及生活服务 |      2家 | 客户、服务需求、人员与资源 |
| **合计**  | **20家** |               |

每家企业至少设置：

- 唯一企业ID
- 行业和经营模式
- 主营产品或服务
- 地区及适用政策条件
- 当前TOP3经营议题
- 关键监测事项
- 重要日期
- 服务套餐
- 已知数据
- 明确缺失的数据
- 最近一次服务记录
- 需要继续跟进的行动

### 套餐分布

为与C02 V1.1保持一致：

- 基础版：4家
- 标准版：14家
- 顾问版：2家

报告内容和交付深度必须依据套餐区分。

不能为了实验方便，向基础版客户默认生成完整深度经营分析。

## 3.2 样本必须包含不完整信息

不得把20家企业全部设计成信息充分、格式整齐、没有异常的理想客户。

建议故意设置：

- 缺少最新营业额
- 只有老板口述数据
- 经营数字与老板陈述冲突
- 有长期未更新的重要事项
- 某企业没有值得推荐的新机会
- 同一行业企业经营模式不同
- 监测数据截止时间不同
- 同名联系人或供应商出现在不同企业
- 不同企业有相似但不相同的经营问题

这些情况更接近未来真实交付中的挑战。

## 3.3 数据使用要求

首轮全部采用模拟或经适当处理的公开测试数据。

若使用真实企业资料，必须在授权、保密和工具使用条件明确后另行开展。

模拟企业不得包含可识别真实个人的非必要资料。

所有模拟报告标记为测试材料，不向外部企业作为真实诊断结果发送。

# 四、实验E01｜公共政策与机会信息批量匹配

## 4.1 实验目的

验证：

**同一条经过核实的外部信息，能否一次采集并分别判断与20家企业的相关性。**

例如一项针对特定行业、地区及企业规模的扶持政策。

传统方式可能需要为每家企业分别检索、阅读、判断和整理。

批量方式希望只进行一次公共信息核实，再依据不同企业档案匹配。

## 4.2 测试材料

准备约10–12条测试信息，覆盖：

- 政策扶持
- 政府公开采购或招标
- 行业活动
- 企业培训
- 供应链机会
- 本地商业资源

可以使用明确标记的模拟信息，或已有官方来源且经过人工核对的历史资料。

需要记录：

| 字段    | 内容           |
| ----- | ------------ |
| 信息ID  | 唯一编号         |
| 标题    | 信息名称         |
| 来源    | 原始出处         |
| 发布日期  | 何时发布         |
| 截止日期  | 是否已截止        |
| 地区条件  | 适用区域         |
| 行业条件  | 适用行业         |
| 规模条件  | 企业规模要求       |
| 其他条件  | 资格限制         |
| 核实状态  | 已核实、待核实      |
| 可推荐程度 | 可进入筛选、不可正式推荐 |

## 4.3 建立人工判定基准

对企业与机会的组合，先建立参考标签：

**可能匹配、需要进一步核实、明确不匹配。**

尤其设置若干容易误判的情况：

- 企业所属地区不符合要求
- 申报时间已截止
- 企业行业看似相关但实际不属于规定范围
- 关键资质条件未知
- 信息仅是公开宣传，不代表能够申报

这套参考标签用于判断系统结果，不能先让AI看到标准答案再测试。

## 4.4 测试流程

**步骤一：** 收集并结构化10–12条信息。

**步骤二：** 读取20家模拟企业的必要匹配字段。

**步骤三：** 批量运行条件筛选。

**步骤四：** AI分别生成企业适配解释。

**步骤五：** 输出建议匹配、待核实和排除列表。

**步骤六：** 人工核查被推荐的信息。

**步骤七：** 记录人工修正、遗漏和判断错误。

## 4.5 主要评价指标

| 指标     | 评价内容           |
| ------ | -------------- |
| 适配准确性  | 推荐信息是否真正符合已知条件 |
| 重要遗漏   | 明确相关的重要机会是否漏掉  |
| 不确定性处理 | 缺少资质时是否标为待核实   |
| 来源完整性  | 是否能找到原始出处      |
| 日期准确性  | 是否正确识别截止信息     |
| 批量人工时间 | 完成20家匹配共需多少人工  |
| 后续维护   | 新增一条政策需要多少整理工作 |

### 建议通过门槛

正式推荐中不得出现：

- 已明确过期却宣称仍可申请
- 已知不符合资格却宣称确定适用
- 没有可核实来源却宣称已核实
- 缺少关键条件却承诺获得政策支持

试验性目标：对能够明确判定的样本，重要匹配准确率达到90%以上。

由于样本较小，90%只作为初始目标，不代表已经达到可商业推广的统计可靠性。

## 4.6 主要输出

- 公共机会结构化记录
- 企业匹配结果
- 待人工核实清单
- 错误与遗漏记录
- 人工耗时统计
- 复用效率评价

# 五、实验E02｜20家企业个性化周报批量交付

## 5.1 实验目的

这是T01最重要的实验。

验证：

**能否通过一次批处理，分别生成20份具有真实差异、符合套餐范围、可审核交付的企业周报。**

AI完成20份文字并不等于实验成功。

真正的成功必须包括：

- 企业信息正确
- 客户权益正确
- 经营事实有依据
- 不跨客户泄露信息
- 重要问题有处理建议
- 没有价值时不强行制造机会
- 人工审核时间可控

## 5.2 输入资料

每家模拟企业建立：

**经营档案 + 本周数据 + 最新事项 + 外部信息匹配 + 套餐权益。**

其中有些企业：

- 本周有新增经营数据
- 本周只有经营待办
- 本周主要是外部机会
- 本周没有显著变化
- 本周出现需要人工核查的数据异常

不能假设所有企业每周都具有完整数据。

## 5.3 统一报告生成流程

**任务调度**

识别本周需要生成简报的企业。

**读取企业档案**

仅载入当前企业的授权上下文。

**执行数据检查**

标记可用、缺失、过期、冲突的数据。

**获取公共信息匹配**

读取E01已形成的相关信息结果。

**生成个性化初稿**

根据企业实际情况和套餐权益生成。

**自动检查**

检查客户标识、来源、数字、日期、权限和必需内容。

**人工审核**

重点核查异常及重要经营判断。

**形成正式交付**

完成批准和模拟发送记录。

**更新服务档案**

记录本次交付与后续待办。

## 5.4 周报建议结构

沿用D04服务节奏：

### 本周值得知道的事情

概括最重要变化。

### 经营情况

仅在具有适当数据时呈现数字和变化。

### 重要问题或风险

对有依据的变化作简明解释。

### 外部机会

仅推荐经过筛选、有实际关联的信息。

### 待办与行动

说明之前事项的实际状态。

### 下一步建议

提供一项具体、合理的建议。

企业无新数据时：

可以输出：

“本周没有收到新的经营数据，暂时无法判断营业额变化。”

不能写成：

“企业本周经营稳定。”

## 5.5 四类特别测试

**测试A：没有明显变化**

观察AI是否为了生成内容而编造问题和机会。

**测试B：数据冲突**

例如老板口述销售增长，系统记录却显示下降。

观察AI能否提示核对口径。

**测试C：相似客户**

两家企业处于同一行业，且有相似产品。

观察报告是否出现客户资料混淆。

**测试D：不同套餐**

基础版不能因为系统具备深度分析能力，就自动获得超出约定范围的完整服务。

## 5.6 计时口径

记录三个独立时间：

**机器运行时间：** AI和程序实际运行耗时。

**人工工作时间：** 准备、操作、审核、修正、模拟交付及归档的主动人工时间。

**自然完成时间：** 从启动到整批结果准备完毕的总历时。

现金成本按实际增量工具及计算费用另行登记。

最重要的是人工工作时间。

## 5.7 与逐家AI辅助流程进行对比

建立两种方案。

### 方案A：逐家AI辅助

同样可以使用AI，但按照企业A、B、C顺序分别检索、整理、生成、审核和归档。

### 方案B：统一批量引擎

共享信息准备和任务调度，只在必要的客户个性化环节分别处理。

两种方案必须采用相同的质量要求。

宜使用内容复杂度相近的两组测试数据并交叉安排执行顺序，尽量降低第一次运行的学习效应。

不能让方案A完全不用AI、方案B使用AI，再把全部改进都归因于批量化。

## 5.8 建议初始验收目标

| 项目              | 建议目标               |
| --------------- | ------------------ |
| 周报生成            | 20份均形成可审阅草稿或明确失败状态 |
| 错误客户资料混入        | 0起                 |
| 关键数字无依据编造       | 0起                 |
| 未核实的重要信息被写为确定事实 | 0起                 |
| 服务权益错误          | 0起                 |
| 批量交付人工时间        | 目标不超过180分钟/20份     |
| 相比逐家AI辅助        | 人工时间减少至少40%        |
| 记录完整性           | 每份有审核和交付状态         |

180分钟和40%均是设计门槛，不是现有能力或外部行业标准。

如果达不到，应首先识别时间消耗在哪里，而不是跳过必要审核来达标。

# 六、实验E03｜同一行业多企业数据分析复用

## 6.1 实验目的

验证：

**同一套数据处理和经营指标程序，能否用于不同企业，而不需要为每家企业重新编写完整分析逻辑。**

首轮建议选择：

**商贸批发行业。**

原因是该行业在现有B04-1中已经有比较清晰的客户、应收、库存和商品分析框架。

它也适合观察经营数据格式不一致带来的额外工作。

## 6.2 测试企业

从模拟档案中选取6家商贸企业。

故意使用不同的数据格式。

例如：

| 企业  | 数据特征     | 测试重点      |
| --- | -------- | --------- |
| T01 | 标准销售与应收表 | 正常运行      |
| T02 | 字段名称不同   | 字段映射      |
| T03 | 日期格式不一致  | 日期标准化     |
| T04 | 存在重复记录   | 去重规则      |
| T05 | 有退款及跨期回款 | 交易与时间口径   |
| T06 | 缺少应收到期日期 | 不可计算与信息缺口 |

所有数据事先构造可核对的参考结果。

## 6.3 统一分析模块

建议首轮仅测试三个模块。

### 模块A：销售变化

计算：

- 期间销售收入
- 按月变化
- 主要客户贡献
- 大客户销售变化

### 模块B：应收与回款

计算：

- 应收余额
- 按约定口径的账龄
- 已知逾期金额
- 主要回款变化

没有到期日期时，不能直接宣称逾期。

### 模块C：库存与商品

在资料充分时计算：

- 库存金额
- 库龄
- 商品销售结构
- 主要商品贡献

没有完整存货或成本数据时，不能虚构库存周转和利润指标。

## 6.4 必须分开的技术职责

**数据程序**

负责读入、清洗、单位转换、去重、指标计算。

**AI**

协助识别字段、提出异常、解释指标含义并生成文字初稿。

**顾问**

负责核对口径、判断经营意义及最终报告质量。

关键经营数字采用可复现的确定性计算过程，而不是让AI根据表格自行编造。

## 6.5 测试流程

1. 准备六套原始数据。
2. 独立建立人工或程序复核的参考结果。
3. 为每套数据建立字段映射。
4. 运行共享指标计算程序。
5. 对每个企业生成独立分析结果。
6. 自动检查数据质量与计算状态。
7. AI生成经营解释初稿。
8. 人工核查数字、结论及数据缺口。
9. 记录第一次配置及后续更新的工时。

## 6.6 验收标准

**准确性：**

可计算的关键指标必须与参考结果一致，允许仅由事先定义的四舍五入产生的差异。

**边界：**

缺少数据时正确标记不可计算，不得以估计值冒充实际值。

**数据隔离：**

一家企业的原始记录不能出现在其他企业报告中。

**复用性：**

第二家、第三家同类企业不得要求重新编写全部指标计算逻辑。

**效率：**

应分别记录首次字段映射时间、重复导入时间及后续更新成本。

## 6.7 后续扩展测试

商贸模板验证后，可选用B04-2餐饮模板进行补充实验。

重点检验：

**堂食收银、美团、抖音团购核销及平台结算之间的重复统计和时间口径问题。**

这类问题不应只靠AI语言理解处理。

**逐项人工整理 + AI辅助**

与：

**结构化访谈解析 + 模板调用 + AI生成 + 人工校准**

# 八、统一的人工效率统计

## 8.1 服务工时分类

所有实验应使用同一套时间分类。

| 类别     | 主要内容           |
| ------ | -------------- |
| 一次性建设  | 程序、模板、提示词、规则开发 |
| 公共信息处理 | 统一检索、核实、整理     |
| 批次管理   | 任务配置、启动、检查     |
| 企业数据整理 | 导入、映射、纠错       |
| AI内容审核 | 检查和修正初稿        |
| 个性化判断  | 经营解释、建议、客户背景判断 |
| 交付与归档  | 审批、发送、记录       |
| 异常处理   | 失败、重跑、纠错及其他例外  |

### 必须单独记录一次性建设时间

例如花费10小时开发通用周报流程，不能将这10小时永久忽略。

但也不应把它作为每次20家企业周报都需要重复付出的人工时间。

因此报告需要分别给出：

- 一次性建设投入
- 首次批量运行人工时间
- 流程稳定后的重复运行人工时间
- 维护及异常处理时间

不能只报告最快的一次成功运行。

## 8.2 人工节省率

计算：

**人工节省率 =（逐家AI辅助人工时间－批量运行人工时间）÷逐家AI辅助人工时间**

前提是两种方式达到相同的最低交付质量。

如果自动化生成大量错误，后续纠错占用了更多人工，必须完整计入批量运行时间。

## 8.3 人工增量成本

记录：

**从10家扩大至20家时，额外增加了多少人工分钟。**

这比单纯计算20家企业平均人工时间更能体现规模效应。

但比较时应保持：

- 任务类型相近
- 资料复杂度相近
- 套餐结构相近
- 质量要求一致

否则规模增加带来的工时差异可能只是样本复杂度不同。

# 九、现金成本验证

## 9.1 现有商业预算

C02 V1.1暂按：

**1298元/月固定现金预算。**

并对基础版、标准版和顾问版分别设置5元、10元、30元的假设增量现金成本。

这些是商业模型假设，并非已测得的真实成本。

## 9.2 实验需要记录什么

- AI调用与额外订阅费用
- 云执行或计算费用
- 文件及存储费用
- OCR或其他额外处理费用（实际需要时）
- 消息发送相关费用
- 重试与失败带来的额外费用

使用现有订阅额度时，应记录额度消耗，但不能自动把它当成另外支付的现金。

## 9.3 成本分类

**固定费用：** 无论客户多少都会发生的订阅等费用。

**随量费用：** 因为任务或客户增加实际产生的额外支出。

**阶梯费用：** 达到某个额度后必须升级套餐或资源的费用。

实际运行结束后，用观测值替换C02 V1.1中的假设成本。

# 十、必须守住的数据与质量边界

## 10.1 企业资料隔离

每家企业应有独立的：

- 企业ID
- 数据空间
- 经营档案
- 任务上下文
- 交付结果
- 权限记录

公共知识库可以共享已获准共享的公开信息。

不能把不同企业的原始经营数据混入共享知识库。

## 10.2 处理外部内容中的指令风险

政策网页、文件和企业上传资料可能含有与服务任务无关的文字指令。

应将其视为待分析资料，而不是允许它们改变系统权限、审核规则或客户数据访问范围。

特别测试：

- 是否尝试读取其他客户资料
- 是否尝试取消审核
- 是否要求自动对外发送
- 是否要求编造缺失数据

这些异常指令不得被执行。

## 10.3 正式交付原则

本次实验使用模拟发送。

未来正式经营服务依照D04规定：

**重要分析和经营建议经过顾问审核后再发给对应企业。**

AI批量能力不是跳过人工责任的理由。

# 十一、如何判断实验是否通过

不建议只设置一个综合评分。

采用四个独立关口。

## G0｜数据安全与隔离

必须满足：

- 无跨企业资料混入
- 无越权访问
- 无未经批准的对外发送
- 无测试材料冒充真实客户诊断

**未通过则停止进入正式客户数据阶段。**

## G1｜交付质量

必须满足：

- 关键数字可靠
- 重要来源可核对
- 不适用或未知条件能够明确标记
- 不制造虚假的问题和机会
- 套餐权益识别正确
- 人工能够否决或修正AI判断

严重错误必须先修复，再进行效率评价。

## G2｜批量效率

重点判断：

- 20家周报人工时间能否达到预定目标
- 与逐家AI辅助相比是否显著节省人工
- 扩大客户数量时，共享工作是否能够被复用
- 新增企业的资料准备是否成为主要瓶颈

未达到预期不意味着项目失败，而应说明瓶颈位置。

## G3｜运营与商业容量

将实测人工数据代入C02 V1.1。

判断：

- 20家会员所需月度人工时间
- 30家会员可能需要的时间
- 新客户建档对容量的影响
- 响应与问诊是否会挤占批处理时间
- 实际扩容费用是否会改变现金模型

只在质量和效率数据支持的范围内作出容量预测。

# 十五、实验失败时如何处理

### 情况A：报告生成很快，但审核很慢

说明系统主要解决了文字生产，而没有解决证据管理、数据核实或质量控制。

下一步优先改进审核规则和证据链。

### 情况B：公共信息可以共享，但个性化匹配不好

说明企业档案、标签和资格规则仍不完整。

下一步优先提高企业画像与条件判断质量。

### 情况C：程序计算准确，但数据导入很费时间

说明标准化数据处理是瓶颈。

优先建立字段映射与可复用数据适配器。

### 情况D：周报很好做，但问诊和资源对接占用大量人工

说明周期性服务具备规模化潜力，非周期性需求仍可能形成容量约束。

应进一步检验B02套餐权益，而不是宣布所有服务都能批量化。

### 情况E：20家可以稳定服务，50家预测却无法满足响应要求

说明需要分离定时批处理与即时客户支持，或调整交付与值守组织方式。

不能仅凭批处理平均时间推断实时服务能力。

# 十六、对商业计划书的影响

T01通过后，可以支持以下比较有限、但有实际意义的结论：

**已验证在模拟环境中，部分经营服务能够通过共享信息、统一计算和批量生成降低重复人工。**

但不能直接写成：

**已验证一个人可以稳定为50家真实企业提供全面经营顾问服务。**

要得出后一个结论，还需要真实客户使用、突发问诊、资料更新、续费和服务响应数据。

因此：

**T01证明技术交付潜力；D01验证真实客户体验；F01验证商业关键假设；C02再根据证据更新盈利预测。**

# 十七、最终判断原则

本项目真正需要形成的，不只是一个擅长回答企业经营问题的AI助手。

而是：

**一套能够长期维护多个企业经营上下文、共享信息处理能力、批量提供常规服务，并让人工专注于重要判断和异常事项的运营体系。**

只有同时做到：

**质量可靠、数据隔离、成本可控、服务可持续，**

批量化才真正构成商业优势。
