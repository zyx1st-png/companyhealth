# 一、系统建设的核心判断

## 1.1 我们究竟要开发什么？

本项目不应首先开发一个面向中小企业的综合经营管理SaaS。

也不应首先开发一个拥有大量独立Agent的复杂智能体平台。

初期真正需要的是：

**一个能够帮助创始人批量服务多家企业、管理例外事项、审核重要结果、跟踪实际成本的运营系统。**

系统要解决的核心问题：

> 当企业从5家增加到20家，甚至30家时，创始人能否仍然清楚知道每家企业正在发生什么、哪些事情需要自己处理、哪些任务已经完成、哪些服务即将逾期？

这里的重点不是系统有多少功能，而是减少重复处理和管理负担。

## 1.2 系统的核心设计

采用：

**一个企业档案底座 + 四个运营引擎 + 一个人工运营驾驶舱。**

四个运营引擎分别为：

1. 共享信息与机会引擎
2. 企业数据与指标引擎
3. 服务任务与批量交付引擎
4. 客户互动与行动跟进引擎

人工运营驾驶舱统一管理这四类引擎产生的结果。

## 1.3 第一阶段只服务创始人

客户侧继续使用：

- 微信
- 约定的企业微信
- 电话
- 文件及截图

企业老板不需要登录新的软件。

后台由创始人操作。

**首先提升顾问服务效率，再根据真实客户需求决定是否建设企业自助端。**

# 二、总体系统架构

建议采用六层结构。

## L1｜客户交互层

承担客户与服务方之间的信息交换。

主要包括：

- 微信消息
- 微信文件
- 企业微信
- 电话访谈
- 人工录入
- 企业主动提交的表格与资料

第一阶段不依赖自动读取微信聊天数据库。

对于无法合法、可靠接入的通信内容，采用人工登记或客户主动提供的方式进入系统。

## L2｜数据接收与企业识别层

承担：

- 文件登记
- 企业身份确认
- 数据归属
- 格式识别
- 授权检查
- 数据质量初筛

这一层必须解决：

**这份资料是谁的？允许拿来做什么？能不能进入下一步处理？**

不能仅凭文件名称猜测企业归属后直接自动处理。

归属不确定的文件进入待人工确认状态。

## L3｜企业经营档案与数据层

这是长期服务的基础。

包括：

- 企业基本档案
- 经营模型
- 老板主要议题
- 历史经营数据
- 企业经营基线
- 企业经营雷达
- 经营发现证据卡
- 服务记录
- 行动计划
- 客户服务权益
- 数据授权信息

每家企业独立管理。

## L4｜任务与智能处理层

负责实际工作。

包含：

- 确定性数据计算
- 共享公共信息处理
- 机会匹配
- AI分析
- 材料生成
- 批量报告
- 待办与监测
- 异常识别

这一层是WorkBuddy和独立计算程序主要发挥作用的位置。

## L5｜质量检查与人工审核层

负责：

- 数据可靠性检查
- 来源核对
- 企业隔离检查
- 服务权益检查
- AI错误检测
- 人工批准
- 退回修改
- 记录审核原因

关键原则：

**AI负责提出结果，系统负责检测问题，顾问负责正式交付的重要判断。**

## L6｜运营驾驶舱

面向创始人显示：

- 今天必须处理的事项
- 待审核的报告和消息
- 各企业服务状态
- 客户问题与资源需求
- 任务异常与数据缺口
- 本月服务人工
- 客户使用和续费情况

驾驶舱不必自己执行复杂AI工作。

它负责把所有任务组织起来，让创始人高效管理。

# 三、第一阶段的五个核心业务模块

## M01｜企业经营档案中心

### 目标

让系统持续了解每一家企业，并能够在不同服务任务中正确使用已有上下文。

### 主要功能

**企业身份**

- 企业编号
- 企业名称
- 所在地区
- 所属行业
- 主营业务
- 联系人
- 服务状态

**经营理解**

- 企业如何赚钱
- 主要客户类型
- 主要产品
- 获客与销售渠道
- 成本结构
- 回款方式
- 关键经营关系

**经营议题**

- 老板当前TOP3问题
- 未来90天目标
- 近期重大事项
- 需要持续关注的问题

**服务资料**

- 首次体检结果
- 历史报告
- 服务记录
- 行动计划
- 经营雷达
- 资料和数据缺口

**商业信息**

- 体验或正式会员
- 套餐权益
- 服务起止时间
- 续费状态

### P0范围

支持手工建档、人工确认AI整理的档案草稿、查看历史记录。

不要求第一阶段就实现完整自动知识图谱。

### 重要规则

企业档案不能只有一段长期累加的自由文本。

建议把稳定事实、当前状态、历史事件和待验证假设分开管理。

避免旧信息不断进入AI上下文，造成错误判断。

---

## M02｜共享信息与机会引擎

### 目标

验证T01 E01提出的：

**公共信息一次处理，多企业复用。**

### 功能流程

**第一步：录入信息**

顾问手工录入或导入公共政策、行业信息、招投标和经营机会。

**第二步：结构化**

AI辅助提取：

- 标题
- 来源
- 发布日期
- 截止日期
- 地区
- 行业
- 资格条件
- 可能适用的企业
- 不确定的条件

**第三步：核实**

顾问检查重要来源和资格要求。

**第四步：批量匹配**

程序先处理确定性条件。

例如：

- 地区是否适用
- 时间是否过期
- 行业是否符合
- 规模条件是否已知

AI再提供企业经营上下文方面的辅助判断。

**第五步：形成推荐候选**

输出：

- 可能匹配
- 待进一步核实
- 不匹配

**第六步：进入审核队列**

由顾问决定是否推荐给某家企业。

### 核心输出

每条机会保留：

**机会ID + 原始来源 + 有效条件 + 匹配企业 + 匹配理由 + 核实状态。**

### P0范围

人工录入公共信息，AI辅助整理，规则匹配，形成待审核结果。

不建设自动爬取全网信息系统。

---

## M03｜企业数据与指标引擎

### 目标

验证T01 E03提出的：

**同一套行业计算程序可以反复处理不同企业的数据。**

### 基础功能

**数据接收**

支持Excel、CSV等结构化资料。

**字段映射**

例如不同企业使用：

- 销售额
- 营业收入
- 实收金额
- 核销金额

系统不能简单认为这些字段等价。

需要按企业业务口径确认对应关系。

**质量检查**

- 缺失字段
- 日期异常
- 重复记录
- 退款与冲销
- 单位不一致
- 统计周期冲突

**指标计算**

由确定性程序运行。

**计算结果保存**

保留：

- 指标定义
- 来源数据
- 计算期间
- 计算规则版本
- 结果
- 数据质量状态

**分析草稿**

AI基于已计算结果形成解释。

### 首批行业

优先：

**商贸批发与餐饮。**

与B04-1、B04-2保持一致。

### 商贸P0指标

- 销售趋势
- 主要客户贡献
- 应收余额
- 有明确到期日的逾期应收

库存分析根据数据成熟度纳入。

### 餐饮P0指标

- 营业额变化
- 订单量
- 渠道收入
- 已知平台费用
- 能够可靠计算的套餐贡献

必须处理堂食、团购券核销和平台结算之间的重复统计问题。

### P0不做

- ERP或POS完整系统集成
- 全行业财务模型
- 自动经营决策
- 无依据的同行平均值比较
- 自动修改企业后台数据

---

## M04｜服务任务与批量交付引擎

### 目标

减少为每家企业重复组织、执行和检查服务的工作。

这是T02的核心引擎。

### 任务类别

| 任务类别 | 示例           | 触发方式    |
| ---- | ------------ | ------- |
| 定时服务 | 周报、月报、月度价值总结 | 日程与套餐   |
| 数据事件 | 新文件、新指标变化    | 已确认数据更新 |
| 客户需求 | 问诊、材料、资源寻找   | 客户提出    |
| 经营雷达 | 日期、指标或事项变化   | 监测规则    |
| 后续行动 | 已安排的客户事项     | 待办时间    |
| 人工创建 | 临时项目或补充分析    | 顾问操作    |

### 每项任务必须知道

- 服务哪家企业
- 属于哪种服务
- 为什么触发
- 使用哪些资料
- 是否符合套餐权益
- 应在什么时候处理
- 谁需要审核
- 当前是什么状态
- 是否已经正式交付

### 建议任务状态

**待接收 → 待处理 → 处理中 → 待审核 → 已批准 → 待发送 → 已发送 → 已归档**

另外设置：

**待补资料、失败、退回、取消。**

不能把AI草稿生成成功直接等同于服务完成。

### 批量运行

例如20家模拟企业周报：

1. 读取本批次应生成周报的企业。
2. 读取各自的授权经营档案。
3. 检查最新数据是否可用。
4. 运行指标计算。
5. 获取已核实的共享信息匹配结果。
6. 生成各企业独立简报。
7. 运行质量检查。
8. 将结果放入审核队列。
9. 顾问集中审核。
10. 分别进行模拟交付和记录。

对某一家企业生成失败，不应让其他19家全部失败。

### 任务可靠性要求

同一任务重复执行时，不能重复创建客户交付或覆盖已经批准的版本。

建议为每个任务保存唯一编号、批次编号、输入版本及执行记录。

失败后支持重新运行，但保留原始失败记录。

---

## M05｜客户互动与行动跟进引擎

### 目标

避免经营支持退化成单纯生成报告。

本模块维护：

**问题被提出以后，是否得到处理？**

### 主要功能

**客户问诊**

登记客户提出的问题及处理进度。

**重要事项**

记录风险、机会、合同日期和经营变化。

**行动计划**

跟进首次体检形成的TOP3行动。

**资源需求**

登记客户需要的财税、法务、供应商、渠道等资源。

**客户反馈**

记录客户是否使用过建议、资料或资源。

### 统一状态

对于行动事项：

- 待确认
- 未开始
- 进行中
- 等待客户
- 等待第三方
- 已完成
- 已取消

### 资源推荐的特殊规则

向第三方介绍企业之前，应确认相关企业愿意对接。

不能因为系统识别两个企业可能匹配，就自动交换双方经营资料和联系人信息。

### P0范围

先支持人工登记、到期提醒、生成跟进草稿和记录结果。

不建设自动商务撮合平台。

# 四、WorkBuddy与其他程序应该如何分工？

建议不要将全部任务都塞进WorkBuddy。

采用三个相互配合的工作单元。

## 4.1 WorkBuddy：AI工作执行与辅助分析

建议主要用于：

- 整理客户访谈
- 提取经营问题
- 生成定向资料清单
- 公共信息初步整理
- 分析经营变化
- 生成周报初稿
- 起草月报及经营材料
- 形成行动跟进建议
- 协助制作PPT和其他复杂文档

这些任务具有较高的自然语言理解、资料理解和文字组织需求。

WorkBuddy是否作为某个任务的自动调用环节，应依据所使用版本、接口和部署条件进行实际验证。

不能把桌面端人工操作能力直接视为稳定的后台API。

## 4.2 Python及确定性程序：数据、规则和调度

建议主要承担：

- 文件登记
- 企业ID核对
- 数据解析与清洗
- 日期处理
- 数字计算
- 任务队列
- 权益判断
- 定时执行
- 数据质量检查
- 权限控制
- 状态保存
- 成本与工时统计

这些工作需要结果可重复、可追溯、可测试。

不宜主要依赖AI临时判断。

## 4.3 驾驶舱：创始人管理和人工确认

负责：

- 查看任务
- 识别异常
- 修改报告
- 批准交付
- 管理服务期限
- 跟进客户
- 查看效率
- 控制服务范围

它应当是一个业务工作台，而不是另一套AI聊天窗口。

## 4.4 推荐的分工原则

| 工作       | 主要负责者          |
| -------- | -------------- |
| 访谈理解     | WorkBuddy/AI辅助 |
| 企业档案最终确认 | 顾问             |
| 数据清洗与计算  | 独立程序           |
| 行业解释     | AI辅助 + 顾问      |
| 公共政策整理   | AI辅助           |
| 政策重要条件核实 | 顾问 + 规则        |
| 批量任务调度   | 独立程序           |
| 周报初稿     | AI             |
| 正式报告审核   | 顾问             |
| 客户身份和权限  | 独立系统           |
| 客户微信正式发送 | 顾问             |
| 服务记录与工时  | 独立系统           |
| 非常规专项材料  | WorkBuddy + 顾问 |

**AI工具可以更换，但经营数据、任务历史和客户关系不能因此丢失。**

# 五、创始人运营驾驶舱的功能结构

驾驶舱首先要回答：

**今天什么事最值得我亲自处理？**

不是首先回答：

“这个月系统运行了多少个Agent？”

## 5.1 首页｜今日工作总览

建议首页包含六个区域。

### A｜今日待办

显示：

- 今日到期任务
- 即将违反响应时效的事项
- 已超期任务
- 待客户确认的事项

每项显示：

**企业、事项、到期时间、当前状态。**

### B｜待审核交付

显示：

- 周报草稿
- 月报草稿
- 经营建议
- 对外重要信息
- 待核实机会

支持进入审核界面。

### C｜重点异常

例如：

- 数据缺失
- 关键指标计算失败
- 经营风险候选
- 客户数据冲突
- 企业文件归属不明
- 批量任务运行失败

系统必须区分：

**经营异常**与**系统运行异常**。

不能将程序失败显示为企业经营风险。

### D｜客户服务状态

显示：

- 当前服务中的企业
- 即将到期的体验
- 即将续费的会员
- 待启动体检
- 待安排会议

### E｜人工容量

显示：

- 本周已使用服务工时
- 下周计划服务工时
- 哪些企业最耗时
- 哪些任务需要人工集中处理

### F｜商业验证

显示：

- 体验人数
- 正式会员人数
- 套餐分布
- 当前MRR
- 客户实际使用
- 续费或退出

商业指标作为重要辅助信息，但不应挤占主要任务处理区。

---

## 5.2 审核中心｜最重要的操作界面

### 列表信息

每条待审任务显示：

- 企业名称
- 任务类型
- 优先级
- 生成时间
- 计划交付时间
- 当前质量状态
- 是否有异常
- 预计审核工作量

### 打开后显示

**左侧：依据**

- 企业档案相关内容
- 计算结果
- 外部信息来源
- 数据质量说明
- 历史待办

**中间：交付初稿**

可查看、编辑正文和必要附件。

**右侧：审核检查**

- 企业归属
- 数字
- 来源
- 推断
- 套餐权益
- 敏感信息
- 后续待办

### 支持的操作

- 批准
- 修改后批准
- 退回重做
- 暂缓并要求补资料
- 取消
- 复制已批准内容
- 标记人工已发送

### 审核原因

至少记录：

- 关键数字错误
- 企业上下文错误
- 重要事实遗漏
- 依据不足
- 建议不适用
- 语言表达问题
- 套餐权益错误
- 数据归属风险
- 其他

不能只记录“修改了”，而不知道为什么修改。

---

## 5.3 企业工作台｜每家企业一张长期服务卡

打开某家企业后，集中查看：

**企业概况**

经营模式、主要联系人、套餐和服务期限。

**当前重要议题**

TOP3事项、风险、机会。

**最新经营数据**

已更新指标和信息缺口。

**待办和跟进**

谁负责、何时到期、当前状态。

**历史服务**

交付的报告、问诊和材料。

**资料与授权**

现有数据类型、处理权限、最近更新时间。

**投入情况**

当月人工分钟数、主要工作类别及额外现金费用。

目标是：

> 创始人不用回忆20个不同微信群的历史，就能够迅速恢复对某家企业的经营理解和服务进度。

# 六、服务权限和套餐规则

系统必须理解三档会员区别。

不是所有客户使用同一套任务模板。

## 6.1 基础版199元

主要任务：

- 企业档案更新
- 外部信息与机会筛选
- 关键日期
- 基础简报
- 基础问答
- 约定的轻材料
- 资源推荐
- 月度服务总结

不默认生成周期性深度经营分析。

## 6.2 标准版399元

在基础版之上：

- 每周经营健康简报
- 月度经营数据简析
- 每月约5次经营问诊
- 每月1份中等材料
- 季度面对面复诊
- 资源推荐及结果跟进

**历史旧权益，已废止用于新客**：现行详B06每周两档。

试运营增加部分单独记录为超配。

## 6.3 顾问版1299元起

增加：

- 深度经营分析
- 月度经营会议
- 约4份中等材料
- 合理范围内持续问诊
- 更深入资源协同
- 约定范围的小型专项分析

重大项目不自动包含。

## 6.4 体验客户99元/30天

使用独立体验任务模板。

不得自动获得全部顾问版权益。

系统记录：

- 体验起止
- 已交付内容
- 额外超配
- 服务工时
- 客户反馈
- 正式转化
- 99元抵扣状态

不自动续费。

## 6.5 服务权益校验

每次任务创建时，系统应检查：

- 客户当前服务是否有效
- 是否属于约定范围
- 本月已使用额度
- 是否属于试运营超配
- 是否需要单独报价

不能仅因为套餐额度达到，就自动拒绝履行已有合同义务。

系统只做识别与提醒，具体争议由顾问按协议处理。

# 七、数据结构设计

原有MVP采用六张核心业务表。

T02不要求第一天全部拆成复杂数据库，但必须明确未来扩展所需的数据实体。

建议至少管理以下十类记录。

| 数据实体    | 主要内容               |
| ------- | ------------------ |
| 企业      | 企业ID、身份、行业、经营模型、状态 |
| 服务合同及权益 | 套餐、时间、额度、服务区域      |
| 授权与数据来源 | 授权用途、资料来源、处理限制     |
| 原始资料    | 文件ID、企业ID、版本、哈希、质量 |
| 指标结果    | 指标ID、值、期间、公式、来源    |
| 公共信息    | 机会ID、来源、条件、有效期     |
| 服务任务    | 企业、任务类型、期限、状态      |
| 交付成果    | 初稿、正式版、审核状态        |
| 审核与工时   | 审核动作、错误、人工分钟       |
| 行动与反馈   | 问题、机会、负责人、结果       |

正式实现时，可以使用独立表，也可在试点期合理合并。

## 7.1 所有企业私有记录必须带企业ID

每项企业资料都应关联明确的企业身份。

不能因为AI能够搜索文件，就允许它搜索所有企业的原始文件。

## 7.2 区分共享数据与私有数据

### 可以进入共享资源库

- 已核实公共政策
- 公开招标信息
- 公开行业资料
- 已获得适当使用许可的通用模板
- 通用指标计算规则

### 不能默认共享

- 企业营业额
- 客户名单
- 内部合同
- 经营诊断
- 原始聊天
- 客户个人资料
- 未公开供应链信息

## 7.3 企业档案需要历史版本

例如：

企业原先认定某客户流失，后来老板解释是主动减少低毛利订单。

系统应保留：

- 最初发现
- 原始证据
- 当时判断
- 企业反馈
- 修订后的判断

不能静默覆盖所有历史信息。

## 7.4 公共信息也需要版本

例如某政策截止时间延长。

必须记录新的来源和核实日期。

原有企业匹配结果可能需要重新检查。

# 八、统一任务数据规范

建议任务至少拥有以下字段。

| 字段                    | 用途         |
| --------------------- | ---------- |
| task_id               | 任务唯一标识     |
| company_id            | 所属企业       |
| task_type             | 周报、问诊、机会等  |
| trigger_type          | 定时、数据、人工等  |
| service_plan          | 当前套餐       |
| entitlement_status    | 权益检查状态     |
| priority              | 处理优先级      |
| due_at                | 应完成时间      |
| status                | 当前任务状态     |
| source_refs           | 使用的来源及数据版本 |
| workflow_version      | 使用的处理流程版本  |
| generation_status     | AI生成结果状态   |
| validation_status     | 自动质量检查状态   |
| review_status         | 人工审核状态     |
| delivery_status       | 交付状态       |
| human_minutes         | 主动人工时间     |
| incremental_cash_cost | 实际增量现金成本   |
| created_at            | 创建时间       |
| completed_at          | 完成时间       |

## 8.1 企业任务与批次任务分开

例如一次20家周报批量运行：

**批次任务：** 2026-W42周报批次。

下面包含20条独立企业任务。

这样可以：

- 统计整批时间
- 单独重试失败企业
- 查看每家企业质量
- 防止错误影响整批结果

## 8.2 应支持安全重试

任务失败或中断后，允许继续处理。

但重跑不能自动：

- 产生第二次正式发送
- 改写已经批准的正式报告
- 覆盖原始数据
- 删除历史错误记录

# 九、经营指标与证据管理

## 9.1 指标不是随时让AI编写的公式

应使用B04-1的指标库思想。

每项指标定义：

- 名称
- 适用行业
- 公式
- 字段要求
- 数据口径
- 时间周期
- 不适用条件
- 输出格式
- 计算版本

## 9.2 数据质量状态

建议至少分为：

**可用、部分可用、待确认、不足以计算、处理失败。**

如果不能计算，应返回明确状态。

例如：

“没有应收到期日，无法确认逾期金额。”

不能默认为零。

## 9.3 与B03证据卡对应

对重要经营发现保留：

- 事实
- 观察
- 推断
- 建议
- 证据来源
- 证据等级
- 数据缺口
- 后续行动

沿用B03的：

**A、B、C、D、U五级证据体系。**

不能用AI的语言自信程度代替证据等级。

## 9.4 AI生成时只读取必要上下文

例如生成企业A的周报：

只允许读取企业A当前任务需要的资料、有关历史记录及已获准使用的公共信息。

尽可能提供结构化指标和必要摘要。

不直接把全部客户原始数据库放入AI上下文。

# 十、自动化执行等级

不建议一开始就追求全部自动发送。

采用四级自动化。

## Level 0｜人工发起，AI辅助

例如临时制作经营方案。

人工提供资料、发起任务、审核并交付。

## Level 1｜程序自动准备任务

例如到周报日自动创建任务、读取对应资料并生成初稿。

顾问审核后发送。

**建议作为首轮MVP的主要自动化级别。**

## Level 2｜自动检测与筛选例外

系统自动执行：

- 来源校验
- 数字核验
- 客户归属核验
- 服务权益检查
- 明显异常提示

顾问对重要结论明确审核。

可以减少重复检查，但不取消必要责任。

## Level 3｜经过验证的限定自动交付

仅作为未来可能选项。

必须同时满足：

- 明确授权
- 通信渠道允许
- 内容风险足够低
- 规则可核验
- 失败可处理
- 可追溯
- 有持续质量监测

例如某些经过客户确认的纯日期提醒，未来可以评估限定自动发送。

但本项目现阶段不将自动发送设为MVP验收前提。

**涉及经营建议、客户敏感信息或重要判断的正式交付，继续遵循B02与D04的顾问审核规则。**

# 十一、驾驶舱如何帮助提高服务效率？

效率改善主要来自四个方面。

## 11.1 减少寻找信息的时间

不用在不同微信群、Excel和文件夹里反复查找企业历史资料。

通过企业ID和任务记录快速获得必要上下文。

## 11.2 减少重复执行

同一条公共政策核实一次。

同一个指标计算程序反复使用。

同一套周报流程批量运行。

## 11.3 减少无效检查

程序先检查数字、日期和数据完整性。

顾问集中查看真正需要判断的地方。

但不能把未被规则发现的问题自动视为不存在。

## 11.4 减少遗忘与管理负担

客户回复、待办和服务期限进入任务系统。

不用主要依赖创始人自己记忆。

这对单人运营尤其重要。

# 十二、必须保留的人工环节

即使T01实验取得积极结果，以下工作仍需要认真评估人工需求：

- 首次经营访谈
- 关键经营模型确认
- 数据异常解释
- 首次体检解读
- 重大问题判断
- 套餐外服务协商
- 资源对接
- 客户关系维护
- 月度顾问会议
- 法律、财税等专业事务转介
- 投诉、差错和数据安全事件处理

因此：

**批量周报效率不能代表整个会员服务效率。**

人工容量模型必须保留非周期性需求。

# 十三、响应时效与任务调度

现行B02服务标准：

| 档位  | 工作时间首次响应要求 |
| --- | ---------- |
| 基础版 | 1个工作日内     |
| 标准版 | 2小时内       |
| 顾问版 | 1小时内       |

建议系统实现：

- 接收时间记录
- 客户套餐识别
- 工作时间计算
- 响应截止时间提示
- 临近超时提醒
- 已响应状态记录

## 13.1 首次响应与任务完成必须分开

客户提出：

“帮我分析一个新店投资项目。”

顾问可能在约定时间内确认需求，并安排正式分析。

但不能把确认需求当作已经完成投资分析。

## 13.2 自动回执不等于顾问首次响应

如果未来增加自动回执，应清晰标记为系统确认收到。

是否满足合同约定的首次响应，依据正式服务标准判断。

## 13.3 单人服务容量提示

系统应提前显示未来若干工作日的：

- 预约会议
- 待交付材料
- 周报审核
- 重要客户事项
- 新客户体检
- 预计人工时间

当服务容量不足时，提醒创始人重新排期或限制新增接单。

# 十四、人工工时与现金成本监测

这是连接T02和C02 V1.1的关键。

## 14.1 工时分为五类

**一次性建设**

开发和修改通用程序。

**共享服务**

公共信息核实、统一任务维护。

**企业固定服务**

周期性简报、月报、审核。

**企业互动服务**

问诊、会议、材料、资源协调。

**新客户启动**

获客、建档、首次体检、结果解读。

不能把共享工时全部忽略，也不能把同一份公共信息研究重复计算20次。

## 14.2 重点观察的七个指标

| 指标        | 经营意义     |
| --------- | -------- |
| 单客户月人工时间  | 客户维护成本   |
| 批量周报总人工时间 | 周期服务效率   |
| 报告平均审核分钟数 | 质量处理负担   |
| 数据更新平均耗时  | 数据标准化程度  |
| 异常及返工时间占比 | 流程稳定程度   |
| 共享任务人工时间  | 规模化时共同成本 |
| 实际额外现金费用  | 边际现金成本   |

## 14.3 对接现有现金模型

C02 V1.1目前采用：

**月固定现金预算1298元。**

以及暂定增量费用：

- 基础版5元/月
- 标准版10元/月
- 顾问版30元/月

上述费用均属于未验证假设。

系统应按实际软件使用量、额外调用、存储、外包及其他费用记录。

固定订阅已经支付的部分不能再按客户数重复扣减。

## 14.4 为未来组织复制保留数据

当前不向创始人强制计提现金工资。

但保留完整人工时间，未来才能测算：

**如果由付薪员工承担同样工作，项目是否仍具有合理经济回报？**

这对应C02的组织复制模型。

# 十五、技术实现建议

## 15.1 建议保留轻量单机路线

原MVP需求已经提出：

- Python
- SQLite
- 本地客户文件目录
- 表格处理程序
- Streamlit操作界面
- 定时任务程序

T02建议将其作为首轮技术实现候选，而不是立刻迁移到云服务器。

具体技术选型仍需经过小规模原型验证。

## 15.2 推荐模块拆分

**数据接收模块**

登记文件、识别类型、检查授权。

**企业档案模块**

读取、编辑、版本管理。

**指标计算模块**

调用行业计算程序。

**信息匹配模块**

处理公共信息及企业匹配。

**AI适配模块**

负责向选定AI服务提交经过筛选的任务上下文，并保存结果。

**任务模块**

创建、排队、重试、状态流转。

**审核模块**

查看、编辑、批准、退回。

**运营统计模块**

计算工时和经营指标。

即使初期使用同一套Python项目，也应保持模块边界。

## 15.3 WorkBuddy集成建议

分为两个阶段。

### 第一阶段：人工协作

顾问通过WorkBuddy完成较复杂的资料理解、方案整理和AI生成任务。

将经过审核的成果保存回系统。

优点：

- 开发简单
- 易于修改流程
- 不依赖未验证接口

缺点：

- 存在手工操作
- 任务执行记录可能分散
- 不适合直接承担全部无人值守批量运行

### 第二阶段：受控集成

如具体版本、授权与接口条件允许，可以利用MCP或受支持的其他集成方式，让AI工作能力与独立系统交换明确范围内的任务和结果。

应首先测试：

- 是否能够稳定调用
- 任务失败如何处理
- 是否能限制企业数据访问范围
- 是否能保留执行日志
- 是否能够控制费用
- 是否适合长期运行

**不要在未完成验证前，把WorkBuddy的桌面能力写成系统必然具备的后台服务。**

## 15.4 系统应避免技术绑定

建议所有AI任务都经过统一适配接口。

例如：

**任务输入 → 授权与上下文检查 → AI服务 → 结构化结果 → 自动检查 → 人工审核。**

这样未来可以调整模型、服务商或执行方式，而不必重建企业档案和任务管理系统。

# 十六、数据安全与风险控制

## 16.1 最小权限

AI只获得当前任务必要的数据和工具。

不得仅依靠提示词要求“不要看其他企业资料”。

应在文件访问、数据库查询和任务执行层落实隔离。

## 16.2 授权与第三方处理

客户资料进入第三方AI服务之前，需要确认：

- 具体处理目的
- 合法授权或其他适用处理依据
- 服务商条款
- 数据保存及模型训练使用条件
- 必要的个人信息与商业秘密保护

不根据厂商的营销描述推定全部敏感数据处理条件已经满足。

## 16.3 原始资料只读

原始文件保留必要版本和来源信息。

计算使用独立处理副本。

避免数据清洗破坏原始记录。

## 16.4 备份与恢复

系统应支持：

- 定期备份
- 合适的加密保护
- 访问限制
- 备份恢复测试
- 客户退出后的数据处理

保存期限依据合同、授权及适用要求确定，不直接把旧MVP中的统一七天删除设定为所有客户资料的唯一处理规则。

## 16.5 模型输出的安全处理

外部文件或网页中可能含有试图改变任务规则的文字。

这些内容只作为资料分析，不作为系统指令执行。

特别测试：

- 诱导跨企业读取
- 诱导取消审核

- 诱导制造数据

# 十七、T01实验如何验证T02？

T02应直接服务于T01，而不是额外增加一套无关的技术指标。

## 17.1 E01｜公共机会批量匹配

- 新增企业是否需要重复检索信息

## 17.2 E02｜20家企业周报

实验样本沿用：

- 基础版4家
- 标准版14家
- 顾问版2家

目标：

**20份分别生成、独立审核、正确归属的模拟简报。**

沿用T01初始验收门槛：

- 跨企业混入0起
- 无依据编造关键数字0起
- 重要未核实事项被冒充确定事实0起
- 服务权益错误0起
- 整批人工时间目标不超过180分钟
- 相比逐家AI辅助目标减少至少40%人工时间

180分钟是周报批次的人工目标，不代表20家企业全部月度服务只需3小时。

## 17.3 E03｜行业数据分析复用

首轮测试6家商贸企业。

检验：

- 不同格式字段映射
- 关键数字正确

- 是否需要大量重新配置

## 17.4 E04｜首次体检处理效率

可选测试：

- 访谈整理
- 行业模板选择
- 经营发现证据卡
- 报告初稿
- 经营雷达
- 30天行动计划

记录人工校准和审核时间。

# 十九、一个完整的使用示例

假设系统已有20家模拟企业。

其中一家商贸企业本周更新销售表。

## 步骤一：接收资料

顾问将文件导入系统。

系统识别可能属于企业T03。

顾问确认企业归属。

## 步骤二：处理数据

程序根据T03的字段映射执行计算。

发现某重点客户采购额连续下降。

## 步骤三：确认数据可靠性

系统检查：

- 数据期间是否可比
- 是否遗漏销售渠道
- 是否存在退货
- 是否与旧数据重复

如果资料不足，只形成待确认事项。

## 步骤四：AI辅助解释

AI结合企业经营模型和历史记录提出：

“该客户采购下降，建议确认是否由于需求、价格或主动订单筛选造成。”

不直接宣称客户流失。

## 步骤五：加入周报

该发现进入T03本周经营简报初稿。

## 步骤六：人工审核

顾问看到：

- 计算结果
- 来源
- 历史记录
- AI初稿

确认后调整建议。

## 步骤七：交付

顾问将批准的内容发送给对应客户。

系统记录交付。

## 步骤八：持续跟进

创建行动：

“本周由企业负责人核实该客户采购变化原因。”

如果老板回复：

“这是我们主动减少了低利润订单。”

系统更新判断及企业经营档案。

下一次周报不应重复使用已经被纠正的流失假设。

**这才是持续经营健康管理所需的技术闭环。**

# 二十、与已有文件的冲突及修订事项

T02形成后，不建议直接覆盖已有MVP需求。

应当先建立版本差异。

## 20.1 原MVP的经营健康评分

原MVP包含经营健康评分及红黄绿展示构想。

但现有B03已明确：

**不使用统一总健康评分作为核心结论。**

因此T02遵循现行B03：

采用稳定、需关注、优先处理、有机会、信息不足等状态表达。

可以有状态标记，但不自动折算为企业总体健康分。

## 20.2 新会员任务容量与旧材料额度

B01/B02旧稿把轻/中等材料按月计数，包括标准版“每月1份中等材料”，**该模型已被2026-10-13新客产品调整替代**，不能把旧份数作为新客权益或系统扣减依据。

正式月费拟试运营任务额度：199元每周**1次定制或2次快办**，399元**2次定制或4次快办**，1299元起**3次定制或6次快办**；1次定制替代2次快办，允许混用但不可相加，未使用次数按合同处理。客户例行简报与已承诺的基础问答**不重复扣制作次数**。具体任务边界和修改规则按B06，合同按G02审查。

技术实现优先手工/简单表格登记企业、服务周、任务类型、占用额度、人工分钟、审核与交付状态，不需要积分引擎；涉及AI输入的客户资料仍遵守作者D1=B、CLAUDE.md、T00和G12的数据分类/授权/供应商核验。旧每月1份中等材料只可作为明确标注的历史情景引用。

## 20.3 自动发送路线

原MVP后续规划曾提出，当修改率较低时评估自动发送。

T02认为：

**修改率降低本身不足以证明自动发送安全。**

还需验证客户授权、数据隔离、重要判断风险、发送对象确认和正式通信渠道条件。

## 20.4 客户数据删除期限

旧MVP提出退出后统一七天删除。

现行D04采用按合同和适用法律处理不同资料的保存、返还和删除。

T02采用D04的分类处理原则，具体期限另行形成数据合规文件。

## 20.5 WorkBuddy的角色

原MVP偏向将WorkBuddy用于手工临时任务。

T02允许未来扩展为AI任务执行层，但不改变：

- 数据主存储独立
- 确定性计算独立
- 关键权限独立
- 正式交付审核独立

是否实现自动集成，依据技术验证决定。

# 二十一、第一阶段验收清单

在投入真实客户数据之前，至少验证：

### 业务闭环

- 能创建企业档案
- 能接收并正确归属文件
- 能计算行业核心指标
- 能生成周报草稿
- 能完成人工审核
- 能记录模拟交付
- 能形成待办和跟进

### 数据正确性

- 关键指标与独立参考结果一致
- 不可计算时明确提示
- 不跨企业使用资料
- 原始文件可追溯

### 审核可靠性

- 未批准的正式分析不能直接进入已发送状态
- 审核修改有记录
- 退回任务可重新处理
- 发送对象需要确认

### 运行可靠性

- 程序意外关闭后可以恢复未完成任务
- 重跑不会重复交付
- 单个客户处理失败不影响其他客户
- 重要状态不会因为重启丢失

### 运营可测量性

- 记录人工时间
- 记录异常与返工
- 记录批次耗时
- 区分固定与增量现金成本
- 能导出T01实验结果

# 二十四、T02最终结论

当前项目真正需要积累的核心技术资产，不是某一套提示词，也不是几十个Agent。

更重要的是：

**企业经营数据与上下文结构、行业计算规则、服务任务体系、质量控制方法以及跨企业复用的交付流程。**

WorkBuddy等AI工具可以帮助我们提高工作效率。

但持续经营服务的关键业务状态应由独立、可控的系统保存。

创始人驾驶舱则负责把复杂的后台处理结果，压缩成少量真正需要人工决策的事项。

未来如果能够验证：

- 公共信息可以反复使用
- 行业分析程序可以复用
- 周期性报告可以高质量批量生成
- 大量常规任务可以自动准备
- 人工集中处理关键问题
- 企业服务质量和客户数据隔离能够保持

那么，本项目才具备从个人经营顾问服务发展为规模化经营支持业务的技术基础。

**系统最终目标不是替创始人生成更多报告，而是让创始人用有限的时间，持续可靠地管理更多企业服务关系。**
